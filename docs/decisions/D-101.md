## D-101: [ANTI-X Y+], [DEVASTATING WOUNDS], [MELTA X] and [LANCE] (24.03, 24.10, 24.25, 24.21, 06.02; M99; amends D-006, D-026, D-051, D-071, D-079, D-096)
**Decided:** 2026-11-27 (M99), **by Claude without the user.** The user asked for the roadmap's Phase 1 to be worked
through without questions ("Don't take my input ... make a note of any decisions you make yourself"). Every choice
below that the rules leave open is marked **(own decision)**; each is the conservative reading, and each is open to the
user's review.

### 1. What M99 takes
The first line of the roadmap's Phase 1 is the weapon abilities still refused when selected (D-071). M99 takes the four
that act on the wound roll, on critical wounds and on the weapon's D:
- **[ANTI-X Y+]** (24.03);
- **[DEVASTATING WOUNDS]** (24.10, with 06.02 Mortal Wounds);
- **[MELTA X]** (24.25);
- **[LANCE]** (24.21).

In the BSData catalogues of the pinned commit these are on about 390 weapon profiles (Devastating Wounds 142, Anti about
170, Melta 68, Lance 13). On the eleven datasheets in `data/units/` they free the Daemon hammer, the Combi-weapon, the
Chainfist, the Reaper autocannon, both Meltaguns, the Strangleweb and the Thunder Hammer. Only the Balefire tome
([PSYCHIC]) is still refused there.

Left for the next milestones: [LETHAL HITS], [PSYCHIC], [CLEAVE], [ONE SHOT], [PRECISION], [INDIRECT FIRE], the
keyword-conditioned forms ("[LETHAL HITS: VEHICLE]", 24.01), a random X ("[SUSTAINED HITS D3]") and a random A on a
melee weapon. They stay refused (D-071).

### 2. [ANTI-X Y+] (24.03)
"Each time an attack is made with an [ANTI] weapon, if the target unit has the keyword denoted by X, an unmodified wound
roll of Y+ is a critical wound."
- **The threshold is part of the attack's profile.** `AttackProfile::critical_wound_on` is 6 (05.02), or Y against a
  target unit with the keyword. It is set when the batches are gathered (`selection_attack_profile`), so D-006 compares
  it. The ability itself is then used up, like [HEAVY], and is not one of the profile's attack-time abilities.
- **A critical wound wounds** whatever the Strength and Toughness (05.02's table: the critical wound row comes before the
  required result). An unmodified 1 still fails first. The threshold reads the unmodified roll, so a wound modifier
  doesn't move it.
- **The keyword** is matched as `has_keyword` matches (case-insensitive; faction keywords count).
  - A series separated by slashes means any one of them (24.01; app 02.05.01).
  - "ANTI-non-X" applies to a unit that does not have the keyword (the FAQ in `docs/gdmissions/core_rules/faq.md`, app
    02.05.01).
  - **(own decision)** A keyword's singular and plural are alike ("Vehicle" / "Vehicles"), as D-099 reads
    EXPLOSIVES/GRENADES. BSData writes "non-Monster/Vehicles" on two profiles.
- **Parsing.** "Anti-INFANTRY 4+", "Anti Vehicle 4+", "Anti-non-Monster/Vehicle 5+", "Anti-Adeptus Astartes 4+". One
  BSData entry has no "+" ("Anti-FLY 2"): **(own decision)** it reads as 2+. A Y outside 2 to 6, or a missing keyword,
  stays unknown text and is refused (D-071).
- **Two instances on one profile** (24.02: "the controlling player must select which instance will apply").
  **(own decision)** Of the instances whose keyword the target has, the lowest Y is used. It is always the controlling
  player's best choice, so no question is asked, as D-071 does for [SUSTAINED HITS].
- **Against the whole unit.** The target unit's keywords are the unit's (02.05). Mixed keywords inside a unit come with
  attached units (19).

### 3. [DEVASTATING WOUNDS] (24.10, 06.02)
"Each time an attack made with a [DEVASTATING WOUNDS] weapon results in a critical wound, the attack sequence for that
attack ends and the target unit suffers a number of mortal wounds equal to the D characteristic of that weapon. These are
inflicted after resolving any normal damage inflicted by those attacks. Mortal wounds inflicted by [DEVASTATING WOUNDS]
weapons can damage a maximum of one model for each critical wound; any remaining mortal wounds inflicted by that attack
are lost."
- **No save roll.** After the wound rolls (and any re-rolls of them, 24.38, 15.02), the batch's critical wounds are
  counted apart (`split_wounds`). Save rolls are made for the other wounds only.
- **"Those attacks" are the batch's** (04.03: the attack dice resolved together). 06.02 says the same: "When resolving
  attack dice, if those attacks inflict a mixture of both mortal wounds and normal damage, resolve all of the normal
  damage first, then resolve all of the mortal wounds." So the order within a batch is: save rolls, 05.04 for the normal
  wounds, then the critical wounds' mortal wounds. The next batch follows.
- **One critical wound, one model (own decision).** 06.02 selects a model for each mortal wound, and 24.10 lets a
  critical wound's mortal wounds damage one model only. Read together: the model is selected once per critical wound, as
  06.02 selects it for the first mortal wound (a wounded non-CHARACTER model first, then any non-CHARACTER model, then a
  wounded CHARACTER, then a CHARACTER). It takes all of that critical wound's mortal wounds, and those it has no wounds
  left for are lost. The rule's own example is this: D 3 against an Intercessor destroys one model and the third mortal
  wound is lost.
  - The other reading would let the defender name a second wounded model for a later mortal wound of the same critical
    wound, and so lose it. With one selection per critical wound that can't be asked.
- **Who decides.** The target's controlling player selects the models (06.02). As for every casualty decision, that is
  one `OrderCasualties` with a full order (D-013), always asked even when forced (D-051).
  - A batch with both normal wounds and critical wounds asks twice: first 05.04 for the normal damage, then 06.02 for
    the mortal wounds. `decision_rule` says which.
  - `preview_casualties` follows the mortal wounds one critical wound at a time, so the client's picks on the board and
    the default order (D-058) work as for an attack.
- **A random D (amends D-096; own decision).** The D is rolled once for each critical wound, by the attacking unit's
  player, each its own Damage roll with Command Re-roll's window, as D-096 rolls a normal attack's. The casualty order
  comes first and the rolls after, as D-096 does for 05.04. The rule's sentence order is the other way (the unit
  "suffers a number of mortal wounds", then models are selected), but the order is a full priority list either way, and
  rolling first would roll dice for critical wounds that are lost when the unit is destroyed.
- **Lost critical wounds.** If the normal damage destroys the unit, the critical wounds' mortal wounds are lost; the
  event says so (`DevastatingWoundsInflicted` with no step).
- **State.** `BatchInProgress::devastating` (the critical wounds) and `mortal` (the normal damage is resolved and the
  mortal wounds are being inflicted). Both are omitted from JSON when unset, so older saves and replays load and save
  byte for byte.
- **Not yet:** 24.28.01 (app-only: with [PRECISION] the mortal wounds go to the selected CHARACTER group first) waits for
  [PRECISION].

### 4. [MELTA X] (24.25)
"If the target unit was within half range of that weapon in the Select Targets step, until the attacking unit's attacks
have been resolved, add X to that weapon's D characteristic."
- The selection already records "within half range" for [RAPID FIRE] (24.30, D-009). With it, X is added to the
  profile's D (`DiceExpr::modifier`: D6 becomes D6+2), when the batches are gathered.
- Models within and beyond half range have different profiles, so they are separate batches (D-006).
- A new target (04.03.03, D-093) is a new Select Targets step: half range is recorded again.
- **(own decision)** With two instances (24.02) the highest X is used, as for [SUSTAINED HITS].
- "[MELTA D3]" (a random X) is not known and stays refused.

### 5. [LANCE] (24.21)
"Each time an attack is made with a [LANCE] weapon, if the attacking model's unit made a charge move this turn, add 1 to
the wound roll."
- `AttackContext::charged` is the unit's `made_charge_move` flag (11.04), read when its attacks start
  (`fighting_context`, and `shooting_context` too: the rule names any weapon).
- With it, a [LANCE] profile's wound modifier is +1, capped with the other modifiers by D-011.
- The flag is omitted from JSON when false.

### 6. The refusals (amends D-026, D-071, D-079)
- `unimplemented_ability_problem` no longer refuses [DEVASTATING WOUNDS]. The "24.10: ... V1 does not implement yet"
  reason is gone. A profile is refused for an ability the engine does not recognise (D-071), or for a random A on a
  melee weapon (D-069).
- **Old files.** JSON written before M99 holds "Anti-INFANTRY 4+", "Melta 2" and "Lance" as unknown text. It is parsed
  again when read (D-071), so such a file gets the ability.
- **List building (D-079).** The freed weapons can be picked, so a new unit takes its BSData defaults again (the Chaos
  Lord's Daemon hammer), every Terminator model type can be taken, and the random armies draw these weapons.

### 7. Bots
- **Odds.** The per-die chances come from core's own wound rolls, so the critical wound chance follows the threshold. For
  a [DEVASTATING WOUNDS] profile a critical wound always gets past the save. The exact outcome counts it as one more
  damaging attack in the batch. The engine inflicts it after the batch's normal damage, on the model 06.02 selects; with
  one allocation group that is the same model. Checked against 20,000 engine batches (`M40_ExpectedDamage`,
  `M99_Odds`).
- **Hypothetical volleys** (`unit_ranged_volley`, `unit_melee_volley`) read [MELTA] and [ANTI] through core's
  `apply_target_abilities`.
- **Not priced:** [LANCE] in the hypothetical melee volley (a charge plan's fight). No datasheet in `data/units/` has it.
- **A profile without these abilities takes the arithmetic it always did**, so play with the old loadouts is unchanged.

### 8. Tests on data that stays refused (own decision)
Each milestone that implements an ability takes weapons off the real refused list, and the tests of the refusal
mechanism (D-026, D-071, D-079, the army builder's greyed options) lost their cases with it.
- They now run on a copy of `data/` built by the tests (`refused_data_root`, `tests/support/army_fixtures.hpp`), where
  D-079 part 1's refused weapons carry an ability the engine will never know ("Conversion").
- Each of those tests also checks the real data's new truth.
- Tests that used [DEVASTATING WOUNDS] as "an ability the engine refuses" use the stand-in instead.

### 9. A bound the user chose: kept on its sample, reported on the new one
`M77_BotDeploy.MeleeUnitsStandNearerTheEnemyThanTheirProposal` requires that melee units are set up nearer the enemy
than core's proposal in more than 30% of their set-ups. The user chose 30% at M90, on the 24 random battles drawn then
(56 of 176, 31.8%).
- M99 makes more weapons pickable, so the same seeds draw other armies. On them the share is **56 of 187, 29.9%**: one
  set-up short of the bound. The deployment code is unchanged.
- **Not changed here.** The bound is still asserted, on the armies it was chosen for (`random_armies_battle_m90_pool`
  draws them from the stand-in data, weapon for weapon: 56 of 176 again). The share on today's draws is printed and not
  bounded.
- **For the user to decide:** whether the bound moves to today's draws (and to what), or stays tied to the M90 sample.
  It is an open item of M99.
